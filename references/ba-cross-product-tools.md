## What each guide covers (paraphrased summary — verify specifics against the live guide)

**Address Book (eoaab).** The universal entity master (Address Book Master F0101, key field AN8) underlying every customer, supplier, employee, partner, and tenant record system-wide — every transaction that touches an entity carries its AN8. A search type (UDC-governed) classifies each record's role (e.g. C=customer, V=supplier/vendor, E=employee, P=prospect); numeric AN8 ranges by type are conventional, not system-enforced. Up to 10 category codes can be defined for the base record via UDC, plus up to 5 "who's who" category codes (01/WO or WT) for individuals associated with a record (contacts at a company) — one category code (07) is reserved for AP 1099 reporting unless 1099 isn't used, in which case it's free for other purposes. Extended attributes live in related tables — Who's Who (F0111), phone (F0115), address-by-date (F0116), parent/child (F0150). Setup: constants (identifier symbols, personal-data-security activation), UDCs, category codes, next numbers, postal codes, and an audit log; optional add-ons include self-service, parent/child organizational structures, date-effective addresses, external email, and word search. A "Copy Category Codes to Customer Master" report keeps AR customer-master category codes in sync with address-book category code changes.

**Foundation Guide (eotfo).** The base Tools-layer setup guide — UDCs, next numbers, and the navigation/personalization framework (roles determine which Navigator tasks and My Pages a user sees; users with multiple roles choose one at sign-in, or via the Navigator menu if permitted). Also documents Task Search / feature security and, from Tools 9.2.5 on, an in-product link to LearnJDE.

**Using and Approving User Defined Objects — UDOs (eotpr).** Governs the lifecycle of user-created web objects — personal forms, grid formats, queries/watchlists, composed/classic EnterpriseOne pages, and (as of later releases) orchestration components share this same lifecycle. Flow: a user builds something → status "Personal" (not shared) → clicks **Request to Publish** → status "Pending Approval" → an approver uses the Work with User Defined Objects application (**P98220U**) to approve (→ "Shared," now visible to other authorized users) or reject (→ "Rework," editable and resubmittable, with an optional rejection note delivered to the Work Center). A shared UDO can be **Reserved** by its owner to edit it further (blocking other edits while reserved). UDO **view security** then controls who can actually see/use a shared UDO — per individual UDO, or `*ALL` for every shared UDO of a given type (except Classic/Composed Pages, which can't use `*ALL` for exactly the reason your `jde-security.md` area file already covers — page-level access must still be explicit); a 9.2.4 `*BASE` value lets an admin restrict users to only their personalized version of a form, hiding the underlying base form. This guide is the one to check for any "why can't I see a shared query/watchlist/grid format/page" question.

**Orchestrator Guide (eotos, current Studio; eotot covers Studio v8 and earlier — check which Studio version is in play before citing steps, since the UI and some component names differ).** An orchestration is a named, callable process (invocable as a REST endpoint or on a schedule) built from reusable subcomponents: **service requests** generally (which subdivide into **form requests** — perform a transaction/query an EnterpriseOne application — and **data requests** — pull values from a table/business view), **rules** (evaluate incoming data against conditions to steer processing), **cross references** (user-defined lookup tables mapping incoming data to EnterpriseOne values), **whitelists** (gate/validate an incoming device or caller against a predefined list), plus **reports**, **watchlists**, **connectors** (REST/DB/notification/other-orchestration calls), **messages**, custom Groovy requests, and **schedules**. At minimum an orchestration needs just one service-request step. Orchestration components are themselves UDOs and follow the same Personal → Request to Publish → Pending Approval → Shared/Rework lifecycle described above, gated by UDO security permissions set per the Security Administration Guide. Runs execute on the AIS (Application Interface Services) Server; the Orchestrator Client is used to test-run an orchestration with simulated inputs before relying on it live.

**Notifications Guide (eotnf).** A notification runs independently of an orchestration to alert users of business events in real time — it can carry boilerplate text plus a shortcut into an EnterpriseOne application, and can be configured to execute a Watchlist or trigger an orchestration when fired. Built via the same Orchestrator Studio interface and typically layered on top of a Watchlist's saved-query criteria (e.g. "notify me by email when this Watchlist's count crosses a threshold").

**One View Reporting (eoaov) / BI Publisher for JDE (eotxj) — how these three reporting layers differ.** JDE has three separate BI Publisher integrations, each for a different audience: (1) **Embedded BI Publisher** turns a UBE's raw output into a "Pixel Perfect" customer-facing document — invoices, statements, pick slips, checks; (2) **One View Reporting** is the end-user self-service layer — users pick fields, apply data selection/sequencing, and build charts/graphs/tables directly from an interactive application, without IT, for their own recurring operational reports (sales/customer/supplier/employee reports they'd run daily/weekly); (3) full **BI Publisher** (the guide covered by eotxj) is for power users/IT building complex ad hoc reports beyond what One View's simplified interface supports. If someone asks "how do I build a report in JDE," which of these three guides applies depends entirely on who's building it and how complex the output needs to be.

**One View Watchlists.** A Watchlist is a saved query rendered as a live counter/alert on a page (e.g. "expenses needing approval," "customers over credit limit," "PO receipts past due"). Watchlists can trigger a Notification (including email, since a 9.2.2 enhancement) when their threshold is crossed, and can be surfaced on UX One role-based pages. A "Run When Selected" query setting should be enabled for a query used as a Watchlist (so it's live) but left off for a query used as a UX One analytic component (for performance).

**Batch Versions Guide (eotbv).** Governs how EnterpriseOne report processing (Universal Batch Engines, "UBEs," named Rxxxxx) actually gets run: you cannot run a UBE without first creating/selecting a **version** of it. A version stores its own processing options, data selection, and data sequencing on top of the report template's master specifications — so the same report (e.g. an AR statement) can have a US-paper/USD version and a France-specific euro/A4 version without duplicating the underlying report object. Versions are typically administrator-controlled at creation but can be modified per run; from the web client, versions are always submitted server-side and run without further user interaction once submitted.
