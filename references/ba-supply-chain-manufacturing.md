## What the core guides cover (paraphrased summary — verify specifics against the live guide)

**Inventory Management (eoaim).** The foundation every other distribution/manufacturing module reads from. An item is set up in two layers: item master information (F4101 — category codes, planner/buyer, applies branch-wide) and branch/plant-specific configuration (Item Branch F4102 + Item Location F41021 — on-hand quantities, GL class codes, location/lot detail). Cost is assigned via a cost method (e.g. 01 purchasing, 02 weighted average, 07 standard) at a chosen cost level (lot, location, branch/plant, or item-master level), stored in the Item Cost table F4105 — a different cost can exist per location/lot within a branch/plant. Purchase-price level setting controls which cost/price table a PO actually pulls from. Supports both generic inventory and production-number-controlled inventory (used by Project Manufacturing) tracked separately in F41021T. Apparel-style items (size/color/length variants) layer a matrix hierarchy (PCW* programs) on top of the same base item structure.

**Sales Order Management (eoaso).** Manages the order-to-cash cycle: order entry (P4210/P42101, including templates, standing/blanket orders, kits, and configured items) → pick slip (R42520) → ship confirm (P4205) → invoice (R42565) → sales update (R42800, which posts to GL and AR). Central integration point is General Accounting via AAIs, plus Accounts Receivable (customer account visibility during order entry), Address Book (ship-to/bill-to addresses), and Inventory Management (allocation, costs). Pricing runs through a flexible base-pricing structure with price adjustments layered on for promotions/discounts — Advanced Pricing (see topic `ba-customer-relationship`) extends this with market-segment, UOM, and date-effective adjustment criteria plus basket/rebate pricing. Country-specific tax/legal requirements exist for Brazil, Chile, Peru, and others.

**Warehouse Management (eoawm).** A rules-driven layer on top of Inventory that models the physical warehouse (location dimensions, temperature, humidity) and item characteristics, then directs putaway, picking, and replenishment via the Location Selection Driver program (seven predefined versions — e.g. Process Putaway/Pick/Replenishment Requests, plus "Resuggest" variants). Putaway/pick/replenishment requests move through a defined status lifecycle (created → suggested → confirmed, or cancelled/partially confirmed along the way); one-phase movement confirms in a single step, two-phase movement stages inventory in a logical/physical staging location first. Supports license-plate processing (full-pallet putaway/pick/replenishment under one LP number), FIFO picking by receipt or lot-expiration date, and a subsystem mode for immediate (rather than batched) request processing — the latter requires matching processing-option setup in Procurement and Sales Order Management to actually trigger it. Only whole units of measure are supported (no decimal-quantity transactions).

**Requirements Planning — MPS/MRP/DRP (eoarp).** Time-phased supply/demand planning using a single core program, R3482 (single-facility) or R3483 (multi-facility), driven by a common set of UDC-controlled quantity types (34/QT — not to be modified, since MPS/MRP calculations depend on it). A generation run reads sales orders, forecasts, planned/firm work orders, rate schedules, purchase orders, and BOM/item-branch data, then produces a time series (the proposed plan), action messages (what to do to rebalance supply/demand), and pegging (traces demand back to its component-level source). You can run a full regeneration or a net-change regeneration (only items flagged as changed since the last run, tracked via a net-change flag on F4102). MPS plans manufactured end items at a single level (not exploded through the BOM); MRP explodes planned orders down through BOM levels starting from low-level code 1. In-Memory Planning Advisor layers a real-time graphical view (prioritized messages, on-hand/days-of-supply alerts) on top of the same planning data for faster action.

**Product Data Management (eoapd).** The engineering/manufacturing-data backbone: bills of material (planning, batch, percent, and manufacturing BOM types), routings, work centers (with costing/accounting info and lead times), and engineering change orders (ECOs, with a configurable approval-routing master). PDM data is read by nearly every other manufacturing module — Requirements Planning explodes demand through the BOM; Shop Floor Management uses BOM+routing to build parts lists and schedule work; Product Costing rolls up BOM/routing/work-center data into item cost; Sales Order Management and Procurement use BOM for kit processing; MPS uses ECO effective dates to time when a product change takes hold in the plan. Setup precedes almost everything else in manufacturing: UDCs/standard procedures for BOMs, manufacturing constants and decimal settings per branch/plant, and work-day/shift calendars.

**Shop Floor Management (eoash).** Executes manufacturing work orders once PDM data (BOM, routing) exists. Flow: create/import work order or rate schedule → attach parts list and routing instructions (auto-generated from the BOM/routing, or entered custom) → check component availability / generate shortage list → issue parts (manual, preflush, or backflush method) → track completions to inventory. Supports kanban-triggered material movement, advanced lot control (split/trace lot origin), co-product/by-product processing, and (with Warehouse Management installed) generating a warehouse picking request instead of a simple parts-list issue. Only supports discrete manufacturing for production-controlled items (Project Manufacturing) — rate schedules, process manufacturing, and cost-detail-by-production-number are explicitly not supported in that mode.

**Product Costing and Manufacturing Accounting (eoapm).** Establishes and tracks the cost of manufactured items. Standard costing (cost method 07) is the default path: simulate cost-component values ("what-if" analysis) → once satisfied, freeze them as the standard → all shop-floor transactions cost against that frozen standard, driving both GL postings and inventory valuation. Actual costing (method 02) instead calculates a work order's built cost from the raw-material and work-center costs actually consumed, without needing frozen cost components. Cost components (freight, taxes, duty, electricity, etc. — hard-coded A/B/C plus user-definable) let you track cost by category; costs can vary by branch/plant and work center for the same item (multifacility costing). The system reports engineering, planned, actual (material/labor), and other variances, and posts detailed or summary journal entries for WIP, completions, and variances via its own AAI tables.

**Quality Management (eoaqm).** Layers test/specification tracking on top of lot-controlled inventory. You define tests, group them into specifications, and optionally set customer-specific preference profiles (e.g. one customer needs tighter tolerances than another) and certificate-of-analysis requirements. Test results are captured at defined points — purchasing, sales order entry, or the work-order cycle — and lots that fail become "nonconforming" and traceable. Requires lot control activated on the items being measured; setup builds on Product Data Management and manufacturing constants.

**Configurator (eoabc).** Guides sales/manufacturing through building a valid configured product from features and options. **Segments** define each configurable feature/option on an item (up to 10 levels of configured items, i.e. multilevel — a configured item can itself contain configured sub-assemblies). **Cross-segment editing rules (CSERs)** enforce valid combinations via if/then/else Boolean logic across segments — e.g. a forklift's boom-height segment might be constrained by its lift-rating segment — supporting upward and downward multi-level referencing and segment-to-segment/cross-branch comparisons. **Assembly inclusion rules** then derive the actual parts, routing, and price/cost for a given configuration, optionally simplified by **configured tables** (a lookup the rules reference, to avoid one rule per combination) and configured item information (F3290, item-level setup: paperwork format, based-on dates for sales/purchase/work orders, whether dynamic configuration entry is active). A configured item can be ordered through Sales Order Entry (P4210), Purchase Orders (P4310), Manufacturing Work Order Processing (P48013), or Engineer to Order — with sales-side variants including quotes, credit orders, direct-ship, transfer, interbranch, and combination orders. Important caveat: manual changes made to a configured order *outside* the Configurator system (e.g. editing the resulting sales order directly) do not sync back into the configuration record — the Configurator is authoritative only for what it itself processed.

**Kanban Management (eoakm).** A pull-based (not push-based) replenishment execution tool — kanbans are visual/electronic cards representing a fixed quantity at a location; when the holding bin empties, checking the card in/out triggers replenishment. The **replenishment source type** (UDC 31/RS) determines behavior: 0=RIP (raw-in-process, no check-in/out transactions, optional), 1=Work Center, 2=Inventory, 3=Supplier, 4=Outside Assembly (checkout creates a sales order for required components; check-in creates a purchase order for the finished product — used for outsourced value-add), 5=Transfer Order, 6=DFM Dual Card (specifies how many cards must check in before replenishment fires). Kanbans can be **one-phase** (completed/received quantity transfers straight to the consuming location) or **two-phase** (an additional Complete transaction is required before material is usable) — inventory kanbans are effectively always one-phase even though two-phase can technically be configured. An item is flagged as kanban-controlled on the Item Master/Item Branch Additional System Information form, which also tells Requirements Planning to suppress MRP action messages for that item (kanban handles its replenishment instead) — except **nonreplenishable kanbans**, explicitly single-use items meant for demand spikes, which *do* still route through MRP. Demand Flow Manufacturing (DFM) has its own kanban setup (pull sequences/pull chains between supply and consumption points) that exports one-way into base Kanban Management via RF31K42E/RF31K30E — DFM-calculated kanban sizes are protected from being recalculated by base Manufacturing's Kanban Size Calculation program (R30450) once exported, and kanbans cannot be exported back from base Manufacturing into DFM.
